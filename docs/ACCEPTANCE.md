# First-release acceptance

`scripts/e2e.mjs` runs the first-release scenario end to end against the built application. The results below are from the run recorded in [`acceptance-report.json`](acceptance-report.json), on Linux (Electron 45 under Xvfb), with real Git repositories, a real Vite dev server, a real Spring Boot application started by `./mvnw spring-boot:run`, and Chromium as "Chrome".

## The fixture

A CaissaTrainer-shaped project (`scripts/e2e/template`): `frontend/` with `npm run dev` (Vite on port 5173, proxying `/api` to the backend) and `backend/` with a Spring Boot 3.3 application on port 8080 and a generated Maven wrapper. It is committed to a fresh repository, pushed to a bare `origin`, and cloned twice: the clone registered in GitManager and a teammate clone that pushes changes during the run.

For automatic discovery the run also builds a home folder (`GITMANAGER_HOME`): `Projects/chess-engine` with a submodule and a linked worktree `Projects/chess-engine-review`, `code/openings`, a repository inside `Projects/site/node_modules`, and one five levels deep.

## Not verified here

- **Discovery on Windows and in WSL 2.** The Windows common locations (`<home>\\source\\repos`, drive-level folders such as `C:\\Projects`, the drive-letter probe), the WSL distribution list and home folder lookup, and the WSL scan running inside a distribution were not run on Windows or WSL. The WSL scan script itself was run with `sh` and `find` on Linux, and the Windows path handling and deduplication are unit-tested; the Windows-only location test runs in CI on `windows-latest`. On a real machine, note that scanning a WSL distribution starts it if it was stopped.
- **The default branch over the network on hosted remotes.** `ls-remote --symref` was tested against a local bare repository, not against GitHub with real credentials.

- **Windows 11 and WSL 2.** The development environment is a Linux container without Windows or WSL. The Windows branches (cmd.exe services, taskkill tree termination, Chrome discovery, Explorer) and the WSL branches (wsl.exe Git, `setsid` process groups, `--list --verbose` parsing, UNC paths, `/mnt` conversion) are covered by unit tests of the exact commands they construct, not by running them. The CI workflow runs the unit and integration suite on `windows-latest` (passing, run 2 of the CI workflow), which exercises the native Windows code for real: Git through Git for Windows, services through `cmd.exe`, tree termination through `taskkill`, including grandchild processes and the forced stop after the grace period. WSL is not available on hosted runners. Please run the scenario on a Windows 11 machine with a WSL repository before relying on the WSL path.
- **The Windows installer on a personal desktop.** CI installs and drives it on `windows-latest` (Windows Server, 1024 x 768, 100 % scaling; see above). Not covered there: a real high-DPI display (only a forced 150 % scale factor), Windows 11's rounded corners and Snap layouts flyout on hover over the maximize button, the tray icon's own mouse handling in the notification area (the scenario triggers the icon's click and menu items in the main process), and an actual sign-in that runs the startup entry (the scenario runs the entry's exact command instead).
- **Real Google Chrome.** The run recorded here used Chromium; the same scenario also passes in CI on `ubuntu-latest`, where the launcher wraps the runner's Google Chrome. Locally it used Chromium through a small launcher script (a separate profile, `--no-sandbox` because the container runs as root, a debugging port so the test can read the tab). GitManager only received the launcher's path as "Chrome location"; on Windows it finds Chrome in its standard install locations.
- **Credential prompts.** The fixture remote is a local bare repository. GitManager leaves authentication to Git (credential helpers work; terminal prompts are disabled because there is no terminal); a remote that needs an interactive terminal prompt will fail with an authentication message instead of hanging.

## Storage acceptance

`scripts/e2e-storage.mjs` (`npm run test:e2e:storage`) drives the built application against `scripts/e2e/fake-gh.mjs`, a stand-in for the GitHub CLI (`GITMANAGER_GH`) that answers `gh api` from a demonstration world of five repositories (one read-only) and applies `DELETE` to it. No network is used and no real repository is touched. The report is written to `e2e-output/storage/report.json`.

**59 of 59 steps passed** (Linux, Electron 45 under Xvfb). They cover: nothing is requested until Scan; retained bytes equal the sum of non-expired artifact bytes; limitations, billing GB-hours, caches and packages are labelled and kept apart; repository list sorting; table filters, search and sorting; evidence and release artifacts Protected and a failed run in Review; a workflow run opens on GitHub; pinning persists locally; the preview totals, grouping, individual selection and exclusions; a dry run sends no `DELETE`; real deletion with GitHub-confirmed counts equal to the selection, protected and release artifacts untouched, the newest two installers per platform kept; the audit log (attempt and confirmed result per artifact, no credentials); automatic safe cleanup refused without approval, deleting only in the approved repository and preserving the newest two builds; Auto Cleanup off by default and its settings persisting across a restart; a missing sign-in and a read-only scope explained, with nothing deleted. Summa-UI's evaluator found 0 failing findings on the overview, the artifact table, the cleanup preview, Activity and Auto Cleanup.

What this does not prove: behaviour against the live GitHub API and a real `gh` session (the sandbox's `gh` token is invalid). Response shapes were checked against real artifact and run responses for this repository; the first scan with a real session is the remaining check, and it is read-only.

The screenshots in the README and [STORAGE.md](STORAGE.md) come from this run and show demonstration data.

## Runners acceptance

`scripts/e2e-runners.mjs` (`npm run test:e2e:runners`) drives the built application against the same stand-in GitHub CLI, extended with the self-hosted runner endpoints (runners, registration and removal tokens, downloads, releases, organizations, runner groups), a registered installation on disk (runner id 42 of `FarmaanFJM/GitManager`, version 2.319.1, a systemd unit recorded), and a stand-in runner package served from a local folder (`GITMANAGER_RUNNER_PACKAGE_DIR`) whose `config.sh` validates the token against the world, registers the runner there and writes `.runner` and `.credentials`, as the real one does. No network is used; the stand-in GitHub lists a busy runner, an offline Windows runner on another machine, a forbidden repository and an organization with a runner group. The report is written to `e2e-output/runners/report.json`; the screenshots in [RUNNERS.md](RUNNERS.md) and the README come from this run.

**62 of 62 steps passed** (Linux, Electron 45 under Xvfb, as root in a container without systemd). They cover: Tools in the sidebar with a minimal landing page; an honest empty inventory that says GitHub was not read; no GitHub request until asked beyond the sign-in check; a discovery folder stored and shown; a scan that lists local, GitHub-only and organization runners once each, with summary counts following GitHub state and manageable told apart from monitoring-only; the real installation path on the local row and "Not inspected" without an invented path for a remote one; the forbidden repository reported as a limitation; search by name and by custom label, the GitHub-only filter, sorting by status; details with the GitHub id, version, default and custom labels, a correct `runs-on` example, an available update stated without pretending, diagnostic logs read from `_diag`, the GitHub settings page opened for that runner; workflow matching (a self-hosted job matched to the right runner, a GitHub-hosted job left alone, labels no runner carries reported, the authorization note); the wizard offering only installable platforms, probing the machine, blocking a service where systemd is absent, refusing to install a blocked plan, showing every command with a token placeholder and the checksum source, requesting no token while planning, waiting for the acknowledgement; the installation itself (all eleven steps, service steps skipped visibly, the runner registered with the chosen labels through a one-time token, files extracted into their own directory, checksum verification in the output, the token nowhere in output, state or configuration); the inventory refreshed without a manual scan; the stacked layout and two-line rows at a narrow width; no start or stop for a runner on another machine; removing a GitHub-only registration with exactly one `DELETE`; unregistering through a removal token with files kept and the leftover flagged; uninstall showing the exact directory and deleting only it; the Settings switches; the inventory and the discovery folder after a restart. Summa-UI's evaluator found 0 failing findings on the inventory, the details and the plan dialog.

What this does not prove: behaviour on Windows (services through `sc.exe`, `tar.exe`, UAC elevation, `Runner.Listener.exe configure --runasservice`), on macOS (launchd agents), on a systemd host (service installation and `systemctl` control), inside WSL distributions, over SSH, and against the live GitHub API with real administration permission. Those paths are implemented from GitHub's documentation and exercised in `npm test` with fakes (149 tests in `test/runners/`, including Windows discovery with simulated `sc.exe` and PowerShell output, systemd, launchd and Windows service control, WSL command construction and SSH quoting); they should be treated as unverified until run on such machines. The first-release scenario could not run in this sandbox (its Maven fixture download is blocked); it is unchanged and runs in CI.
